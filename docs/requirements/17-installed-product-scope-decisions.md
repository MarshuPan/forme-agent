## 1. 产品形态

用户安装的是一个完整的 forme 产品。它不替换用户的操作系统，但在现有系统上以 appliance-like 的方式提供自己的常驻服务、数据目录、账号和 Web 控制面；操作系统负责服务监管。用户通过网页完成初始化、登录、对话、项目管理、审批、配置与维护。关闭网页不结束任务，退出网页账号不停止大脑，操作系统用户注销不停止系统服务。

安装包是交付方式，常驻服务是运行方式，二者同时成立。不要求用户安装 Rust、Node.js、运行 cargo 或手工启动多个终端；不制作桌面客户端，不依赖托盘存活。Web 不是外部应用的桥接页，而是这个 ForMe 实例的统一控制面；底层可以有多个受保护进程，但用户不需要认识或分别管理它们。

主机休眠、关机、断电时，本机任务无法继续。希望日常电脑关闭后仍持续工作，应把唯一大脑安装在常开主机；其他设备作为网页客户端或受治理 executor 接入。不能用“常驻”宣传物理主机关闭后仍在计算。

## 2. 产品化需求

本文使用 **P01–P16** 表示产品需求，验收使用独立的 **IP01–IP24**。它们不占用 S1–S99、C1–C24 或历史 A/B/C/D 波编号。

| 需求 | 必须实现的行为 | 关键边界 |
|---|---|---|
| P01 整体安装 | Windows、macOS、Linux 各有原生安装入口，安装程序部署完整组件并注册系统服务。 | 无开发工具要求；平台目标和实际支持分别记录。 |
| P02 系统常驻 | 随系统启动、崩溃恢复、受控停止；浏览器关闭或 OS 用户注销后继续非交互工作。服务启动后，固定产品地址应在秒级进入登录/初始化/状态页面；主脑 readiness 可以随后异步到达。 | 不把登录启动项、终端后台进程等同于系统服务；Web 可达不等于主脑已就绪。 |
| P03 单脑装配 | 正式 CLI、Web、scheduler 仍使用同一 ProductionRuntime、owner、权威 store 和 writer；所有入口属于同一个 ForMe 产品实例，用户只面对一个产品地址。 | 浏览器、维护进程、workspace 与 worker 不拥有独立认知；内部进程边界和内部地址不构成产品分裂。 |
| P04 无配置可初始化 | 大脑尚无模型/密钥/owner 配置时，管理入口与初始化页面仍可启动。 | 完整大脑 doctor 通过前不接受任务；故障不自动创建空脑。 |
| P05 安装认领 | 本地一次性凭据证明安装管理权，再创建账号密码并绑定唯一 owner。 | 非“第一个访问者就是管理员”；局域网不能抢占安装。 |
| P06 登录与身份 | 唯一 `SuperAdmin/Owner` 的账号密码登录、会话撤销、密码更改和本地恢复；该账户拥有产品控制面完整权限。 | 不设计普通 Web 角色/多租户；登录账号、稳定 OwnerId、OS 服务身份、Agent 行动授权分离。 |
| P07 配置持久化 | 网页配置模型、消息渠道、工作目录、能力、代理和安全选项；校验、保存、启用状态可区分。 | 密钥只写不回显；环境变量兼容开发，不能静默覆盖已保存配置。 |
| P08 本地与 LAN | 本地产品地址可直接打开；显式启用后支持受认证的局域网 HTTPS。 | 内部 Runtime Ingress/Gateway 继续 loopback；不默认公网开放；证书信任不能虚报。 |
| P09 特权与隔离 | 安装获得必要系统管理权；日常 Web/大脑/工具分权；系统操作走受限 helper。 | 安装提权不等于模型拥有任意 root/SYSTEM 命令；仍走 Harness。 |
| P10 数据可恢复 | 数据、配置、密钥、日志、工作目录与程序版本有明确归属；无交互重启仍能读原脑。 | 密码不是唯一数据密钥；恢复到新路径并显式切换 authority。 |
| P11 生命周期 | 升级、停服、回滚、卸载有事务、备份、恢复与状态反馈。 | 未知副作用不重放；卸载默认保留数据；回滚代码不等于撤销外部动作。 |
| P12 对话工作台 | 会话、流式回答、附件、真实步骤、审批、产物与错误在同一交互中呈现。 | 只消费正式协议/事件；不直调模型，不伪造隐藏思维链。 |
| P13 长期项目 | workspace 目标、约束、历史、长期任务、监管与重新协调可查看和控制。 | 项目思考仍属于主大脑；workspace 不是第二 Agent。 |
| P14 待办与认知 | 收件箱汇总主动建议/问题/审批/失败；认知页面支持证据、候选、纠正、撤销与遗忘。 | 点击查看不是采纳；采纳建议不自动增加权限。 |
| P15 维护可达 | 核心失败时仍可登录诊断、修复配置、检查备份并受控恢复。 | 维护入口不是绕过 policy 的通用 shell 或第二 writer。 |
| P16 前端限定复用 | 采用 DeepSeek 的页面结构、可分离组件和对话交互经验。 | 仅许可审查通过的前端白名单；不引入其内核、插件架构或服务端。 |

P02 的“秒级可达”定义为：在受支持平台上，从 OS 服务管理器确认 Web 控制面进程进入 `Running` 起计，固定本地 Product URL 在 **5 秒预算内**返回可渲染的登录、初始化、维护或启动页面；不把浏览器进程启动和操作系统整机启动时间计入该预算。模型连接、历史脑校验和 BrainReady 可以更慢，但不能阻塞 Web shell，也不能以空白页或无限 spinner 掩盖真实状态。该预算在每个支持平台的 IP01/IP02/IP04 证据中单独记录。

### 2.1 Appliance 参考：飞牛 fnOS 与 ForMe 的对应边界

2026-10-28 对飞牛官方产品页及帮助中心的安装、访问、端口、配置恢复和账号说明进行了核对。飞牛的关键经验不是某个页面样式，而是“安装后得到一个持续运行的设备级产品，浏览器进入该产品的初始化和管理界面”：系统启动后通过浏览器访问设备地址，首次访问完成设备名称和管理员账号设置；本地账号负责设备内登录，云端账号只在使用其远程服务时参与；端口和系统配置由 Web 设置统一管理。

| 飞牛 fnOS 的可核实行为 | ForMe 的对应设计 | 不复制的部分 |
|---|---|---|
| 系统镜像写入设备，系统启动后自身持有服务、数据和 Web 入口 | ForMe 用原生安装器部署 release、数据目录和 OS 常驻服务，在宿主 OS 之上形成软件 appliance；启动后用户只认一个 Product URL | 不刷写/替换宿主 OS，不把 ForMe 伪装成完整 NAS 操作系统 |
| 首次启动后浏览器进入初始化，创建本地管理员账号，再进入桌面 | 安装后 Web 先进入认领/初始化；唯一账号同时是 `SuperAdmin/Owner`，配置有效后 Host 自动启动 Brain，ready 后进入同一工作台 | 不增加第二套云账号、多租户或普通 Web 角色 |
| 本地登录、系统设置、应用/服务状态由同一个系统 Web 控制面承载 | 对话、workspace、收件箱、记忆/认知、模型/能力设置、维护、备份/恢复和服务状态都属于同一个 ForMe 控制面 | 不引入飞牛的存储池、媒体、应用中心或其服务端/插件体系 |
| 端口修改会影响访问并需要明确提示；HTTPS、证书和远程访问是独立配置 | Web 网络配置是版本化产品事务；默认 loopback，LAN 必须显式启用 HTTPS/Host/Origin/防火墙边界，切换失败回到可维护的 loopback | 不默认公网开放、不把发现或 mDNS 当认证、不自动修改防火墙 |
| 配置备份/恢复区分系统配置与数据，并说明版本和缺失依赖 | ForMe 分离程序、产品配置、认证、脑数据、密钥、workspace 和备份；恢复必须先校验、再由 owner 显式切换，未知结果不能重做 | 不把网页登录成功当作数据恢复完成，也不以空脑覆盖旧脑 |
| 设备关闭网页、拔掉显示器后系统仍由主机运行 | 关闭网页、退出登录、宿主用户注销不停止非交互任务；WebAvailable 与 BrainReady 分开展示 | 主机休眠、关机、断电时本地计算停止；不能宣传“电脑关机后仍运行” |

这项参考把 ForMe 的产品模型固定为：

```text
一个安装实例 = 一个 Product URL + 一组 OS 常驻服务 + 一个认证 Owner
              + 一个 ProductionRuntime/主脑 + 一套持久数据/配置/恢复状态
```

用户不需要认识 `forme-webd`、`forme-hostd`、`forme-gatewayd` 或 worker。它们只是为了权限、故障和生命周期隔离而存在的内部单元；Web 与主脑仍然是同一个 ForMe 产品的两个运行面。关闭网页不停止服务，登录也不是启动主脑的开关。

## 3. 交付形式与平台目标

| 平台 | 交付选择 | 常驻机制 | 首批验证目标 |
|---|---|---|---|
| Windows | 签名 `.exe` 安装器，采用 Inno Setup 构建；版本/许可证进入构建清单。 | 原生 SCM 服务，使用受限服务身份及独立管理 broker。 | Windows 11 x86_64。 |
| macOS | Developer ID 签名、notarization 的 `.pkg`。 | 系统 LaunchDaemon；桌面交互另有登录会话 helper。 | macOS 14 及以上的 arm64/x86_64，逐目标验证。 |
| Linux | `.deb`、`.rpm`；统一入口检测系统并安装对应签名包。 | 系统级 systemd 服务与专用账户。 | Ubuntu 24.04 LTS x86_64/arm64；Rocky Linux 9 x86_64。 |

上述是**发布目标，不是当前兼容性声明**。不支持的系统/架构须在安装前给出明确结果，不运行未经验证的安装脚本兜底。容器、WSL、其他 Linux 发行版、Windows ARM 和无 systemd 系统不因“能编译”自动进入支持范围。

完整产品包含编译后的 Web 静态资源，不要求常驻 Node 服务。浏览器、Python 等可选执行依赖按能力分级：缺失时显示具体能力不可用，可从受控安装流程补足；不因某个可选工具缺失阻止对话、配置或维护。

## 4. 用户完整路径

1. 从可信来源获取并运行安装入口；系统确认安装/服务注册权限。
2. 安装程序部署组件、初始化受保护目录，注册并启动管理与 Web 服务，在调用安装器的用户会话打开唯一产品地址；无桌面时输出访问说明。用户不需要启动终端、选择内部端口或理解进程拆分。
3. 用户使用本机一次性证明进入受限初始化，先选择新脑或验证已有脑/备份，再创建账号密码并完成认领，绑定正确的唯一 OwnerId。
4. 用户配置模型、密钥、代理与 workspace；逐项看到校验结果以及“已保存/自动启动中/已生效/待修复”。
5. Host 自动启动或受控重启 Brain；doctor 通过后核心服务装配唯一 ProductionRuntime。网页先显示真实的初始化/启动/维护状态，ready 后自动进入完整工作台；正常路径不要求用户手动“启动主脑”。
6. 后续通过账号密码登录同一大脑。长任务和主动认知由后台持续运行，网页只负责控制与展示。
7. 升级、备份、恢复、网络暴露与密码恢复使用独立维护流程；它们不改变 OwnerId，也不静默清空原脑。

## 5. 权限与“最高权限”的含义

网页是唯一产品控制面，登录账户是唯一产品 `SuperAdmin/Owner`，对当前产品控制面拥有最高完整权限。初始化、对话、workspace、审批、认知查看/纠正、配置、备份/恢复、服务维护和可用能力状态都从这个控制面进入；CLI/hostctl 只保留给无 Web、恢复或运维场景的受限入口。产品具有安装系统服务、设置必要文件权限和完成经授权系统操作的能力。**权限由受控组件持有并按操作授予**，不把 Web 请求、模型输出或工具 shell 直接运行成最高权限。

SuperAdmin 的“最高”只表示产品控制面没有更高的 Web 角色；它不绕过固定内核治理，也不等于 Agent、模型或任何工具获得 Windows `SYSTEM`、Linux `root`、macOS `root` 或任意 shell。高风险操作的重新认证是具体 operation 的二次绑定，不是第二个账户或角色。

Agent 发起系统动作时，仍须最终 plan、当前 policy、能力门、permission/envelope、审批摘要、one-shot 消耗和审计。owner 在维护页面执行安装/修复服务属于明确的管理员操作，接口只接受规定的维护类型；模型不能通过工具调用该维护通道。

桌面控制还依赖目标用户处于可交互会话以及相应 OS 许可。锁屏、注销、macOS TCC 拒绝等必须显示“桌面能力不可用”；后台对话、认知和非交互任务可继续，不能以系统服务身份绕过 OS 隐私限制。

## 6. 前端范围

工作台固定五类主要入口：**对话、工作空间、收件箱、记忆与认知、设置**。主布局为左侧导航/项目、中间会话、右侧详情/产物；窄屏允许折叠，不照搬桌面壳。

DeepSeek 只提供 UI 结构与可审查的前端复用来源。所有业务状态、模型、编排、记忆、插件、MCP、治理、数据与调度继续使用 forme 已有体系。无法脱离其宿主框架的组件采用 forme 自有实现，不为复用视图引入 Cordis 或另一套运行时。边界见 [frontend-reuse-policy](../compliance/frontend-reuse-policy.md)。

## 7. 非目标与完成含义

本轮不增加多租户、家庭多账号权限体系、公网托管平台、移动/桌面客户端、云同步主脑、自动外发或新的能力市场。局域网访问不是 M4 peer trust 的替代；网页登录也不授予 executor 身份。

文档完成只表示范围、架构、实施契约和验收已写出；安装成功、服务可用、跨平台支持、UI 可操作和真实任务价值必须在后续实施后分别取得证据。历史内核验收继续有效，但不能冒充这些新能力的验收。
